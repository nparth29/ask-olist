# Design Decisions

One entry per choice: what we chose, the main alternative, and why (written for a fresher).

## D1. LLM model: `gemini-3.5-flash`
- **Chosen:** `gemini-3.5-flash` (set once in `src/ask_olist/config.py`).
- **Alternative:** `gemini-3.8-flash` (the newest Flash) or `gemini-3.1-flash-lite` (faster, weaker).
- **Why:** On 20 Nov 2026 the 3.6/3.7/3.8 Flash models timed out or returned 503 "high demand". 3.5-flash worked (about 18 s for a tiny prompt). Model names live only in `config.py`, so switching later is a one-line change (but a new model name means a new cache key).

## D2. `pyproject.toml` with editable install
- **Chosen:** a minimal `pyproject.toml` and `pip install -e .` so `python -m ask_olist.smoke` works with the `src/` layout.
- **Alternative:** setting `PYTHONPATH=src` by hand each time.
- **Why:** the editable install works the same in PowerShell and Command Prompt and needs no extra dependency.

## D3. Local-only files are git-ignored
- **Chosen:** `.env`, `data/`, `cache/`, `logs/` and `.venv/` are listed in `.gitignore`, so they are never committed or pushed.
- **Alternative:** commit them.
- **Why:** `.env` holds the API key; `data/` holds the licensed dataset (CC BY-NC-SA 4.0), which must not be republished; `cache/`, `logs/` and `.venv/` can be rebuilt.

## D4. Zip prefixes stored as TEXT
- **Chosen:** all `*_zip_code_prefix` columns are TEXT. Other numbers are INTEGER/REAL, timestamps are ISO text.
- **Alternative:** INTEGER, as the CSV suggests.
- **Why:** zips like `09790` have a leading zero. As integers they become `9790`, and a text/number mismatch could silently break joins. We never do maths on a zip.

## D5. Build the database with pandas, rebuilding from scratch
- **Chosen:** `build_db.py` reads each CSV as text, converts types explicitly, creates the tables with `CREATE TABLE`, and deletes and rebuilds `olist.db` on every run.
- **Alternative:** let pandas guess the types, or update the existing database in place.
- **Why:** guessed types can change between runs; an explicit schema is predictable. A full rebuild means there is no half-updated state. Timestamps are parsed and re-formatted, so a bad value fails loudly instead of slipping in.

## D6. Trap evidence is generated by code
- **Chosen:** `scripts/check_traps.py` runs one SQL check per trap and writes `reports/data_traps.md`.
- **Alternative:** run queries by hand and paste the numbers.
- **Why:** rule 4 says no invented numbers. If a number is in the report, a query in this repo produced it, and we can re-run it.

## D7. What text-to-SQL is, and why the schema goes in the prompt
- **Chosen:** the whole `schema/schema.md` (tables, columns, join keys, trap rules) is pasted into every SQL prompt.
- **Alternative:** let the model guess table names, or fine-tune it on our schema.
- **Why:** an LLM has never seen our database. It only writes correct SQL if it can read the real table and column names, and our rules for the traps. Pasting the schema is cheap, needs no training, and is easy to change.

## D8. No LangChain or LlamaIndex
- **Chosen:** plain Python: one function per step (prompt, LLM call, guard, run, answer).
- **Alternative:** LangChain or LlamaIndex.
- **Why:** Parth must be able to explain every step in an interview. Frameworks hide the steps behind many layers, and the pipeline is small enough to write directly.

## D9. Structured JSON output from Gemini
- **Chosen:** Gemini must reply with JSON `{sql, assumptions}` (a response schema is passed to the API), with temperature 0.
- **Alternative:** ask for free text and cut the SQL out of a markdown code block.
- **Why:** parsing free text breaks when the model adds extra words. A schema gives us two clean fields, and `assumptions` lets the answer say which definition was used. Temperature 0 keeps answers as repeatable as possible.

## D10. Disk cache for every LLM call
- **Chosen:** each call is saved in `cache/` under sha256(model + prompt version + input).
- **Alternative:** no cache, or an in-memory cache.
- **Why:** a re-run makes zero API calls, which saves free-tier quota and time (a repeat question took 1.1 s instead of about 90 s) and makes evaluation numbers repeatable. The key includes the model and prompt version, so changing either never returns a stale answer.

## D11. Retry on 429, 503 and 504 with exponential backoff
- **Chosen:** wait 2 s, 4 s, 8 s ... (up to 5 retries) on 429 (rate limit), 503 (overloaded) and 504 (timeout).
- **Alternative:** retry only on 429, as the spec says.
- **Why:** on 20 Nov 2026 the Gemini Flash models returned 503/504 under load. Those errors are temporary just like 429, so waiting and retrying is the right response. Other errors (like a bad API key) fail straight away.

## D12. Guard design: sqlglot parse, one SELECT, plus a read-only connection
- **Chosen:** the guard parses the SQL with sqlglot and accepts exactly one statement that is a SELECT (a leading WITH is fine, and UNION of SELECTs is allowed). It rejects PRAGMA, ATTACH, DDL and DML anywhere in the tree. Then the query runs on a connection opened with `mode=ro` plus `PRAGMA query_only=ON`.
- **Alternative:** a regex that blocks words like DROP, or trusting the prompt ("only write SELECT").
- **Why:** an LLM must never be trusted to run DELETE. A regex is easy to fool, but a real parser sees the structure. The read-only connection is a second, independent lock: even if the guard had a bug, SQLite itself refuses to write. The row cap (1000) and 10 s timeout stop runaway queries.

## D13. Thinking level: tested `low`, NOT adopted (default kept)
- **Chosen:** keep the model's default thinking (`LLM_THINKING_LEVEL = None` in `config.py`). The option stays in `llm.py` and is part of the cache key, so it can be tested again.
- **Alternative:** `thinking_level="low"`, hoping for faster answers.
- **What we tested (20 Nov 2026):** the same 5 sample questions, default thinking vs `low`. Only 4 of 5 could run; the 5th hit the free-tier daily limit (see D14). The rule was "keep `low` only if all 5 answers match".
- **Result:** Q1 and Q4 gave the same rows and the same numbers (Q1's answer was written as a numbered list). Q2 gave the same value (5,962,902.01), but with a different column name. **Q3 changed:** default thinking answered 2,997 repeat customers (all order statuses); `low` answered 2,801 because it added `order_status = 'delivered'`, which the question did not ask for. So `low` misapplied rule 4 (the delivered default is for sales and revenue questions).
- **Speed:** no clear gain. Old (first run) vs new (estimated from cache file times): Q1 85.6 vs 157.4 s, Q2 118.6 vs 106.6 s, Q3 172.0 vs 97.3 s, Q4 90.3 vs 106.4 s. Both include waiting on 503/504 retries, so server load hides any real effect. The new times are estimates, not measured by the pipeline.
- **Why:** accuracy matters more than a speed gain we could not see. One changed answer is enough to reject it.

## D14. Free-tier daily limit
- **What happened:** on 20 Nov 2026 Gemini returned `429 ... requests per day limit exceeded on Free Tier, limit: 20`. The message named `gemini-3.6-flash`, although `config.py` uses `gemini-3.5-flash`; we have not found out why.
- **Impact:** every question costs 2 LLM calls (SQL, then answer), plus retries. About 20 calls a day is roughly 10 questions a day. The Phase 5 evaluation (30 questions x 2 configurations) will not fit in one day. This is open and needs Parth's decision.

## D15. The agent loop: feed the error back, max 2 retries
- **Chosen:** if the guard rejects the SQL or SQLite raises an error, we send Gemini its own SQL plus the exact error (`prompts/fix_v1.txt`) and run the new answer through the same guard and read-only connection. At most 2 retries (3 attempts in total). Every attempt is written to `logs/runs.jsonl`.
- **Alternative:** give up on the first error, or keep retrying until it works.
- **Why it works:** most first-attempt failures are small (a wrong column name, a missing alias). The error message says exactly what is wrong, and the model can see the schema and its own mistake, so it can fix it. **Why only 2:** if the model has not fixed it after two tries it is usually misunderstanding the question, and more tries only burn time and free-tier quota. The retry never skips the guard.
- **Tested with a mock** (`tests/test_pipeline.py`): bad first SQL, good second SQL; a DROP rejected by the guard and then fixed; and giving up after 3 failed attempts.

## D16. Fail fast when Google says "retry in hours"
- **Chosen:** if a 429/503/504 error says to wait more than 60 seconds (Google's `retryDelay`), we raise at once instead of backing off. Short delays still use 2 s, 4 s, 8 s ... backoff.
- **Alternative:** always back off up to 5 times.
- **Why:** the free-tier daily quota says to wait about 12 hours. Retrying wastes about a minute per call and cannot succeed. Tested in `tests/test_pipeline.py`.

## D17. Run `ANALYZE` when building the database
- **Chosen:** `build_db.py` runs `ANALYZE` once after loading and indexing. This stores table statistics in the database file.
- **Alternative:** nothing (SQLite's default), or letting the app run ANALYZE.
- **Why:** without statistics SQLite chose a very slow join plan for a simple "top 10 sellers by revenue" query: for every item row it built a temporary index on `orders(order_status)` instead of using the `order_id` index. The query hit our 10 second timeout. With statistics it runs in well under a second. We run it at build time because the app must never write to the database.

## D18. 30 drafted examples, checked by a human
- **Chosen:** `examples/examples.yaml` was drafted first (30 question and SQL pairs, all `verified: false`). `scripts/check_examples.py` runs each on the read-only database and writes `reports/examples_check.md`. Only Parth sets `verified: true`; only verified examples go into the RAG index.
- **Alternative:** let the LLM write the examples and index them straight away.
- **Why:** examples teach the model by showing correct SQL. A wrong example would teach a wrong pattern, and the evaluation would then be measuring our own mistakes. They cover all 9 tables and all 8 traps (each has a `traps` list). The script also checks the numbers against Phase 1 where they overlap (for example 2,961 orders with several payments).

## D19. Embedding quota is separate from the LLM quota (one test call)
- **Test:** on 20 Nov 2026, after the Flash daily quota was used up, one `gemini-embedding-001` call succeeded (3072 numbers per vector, 0.9 s).
- **What this shows:** embeddings are not blocked by the exhausted generate-content quota, so building the example index should work today.
- **What it does not show:** the embedding model's own daily limit. One call cannot reveal that, so we will cache every embedding (rule 6) and embed each text once.

## D20. What RAG means here: embeddings, FAISS, cosine similarity
- **Chosen:** every verified example question is turned into a vector of 3072 numbers (an *embedding*) by `gemini-embedding-001`. Questions with similar meaning get vectors that point in similar directions. We scale each vector to length 1 and store them in a FAISS `IndexFlatIP`. For a new question we embed it the same way and FAISS returns the 3 stored vectors with the highest inner product. For length-1 vectors the inner product *is* the cosine similarity (1.0 = same meaning, 0 = unrelated). The 3 examples (question and SQL) go into the prompt.
- **Alternative:** a fixed set of examples in every prompt, or keyword search (matching words).
- **Why it helps:** the model sees working SQL for questions like the one it must answer, including how the trap rules are applied (CTEs, `customer_unique_id`, delivered filter). Keyword search would miss "slow delivery" against "late delivery"; embeddings match on meaning. With only about 30 vectors an exact search (`IndexFlat`) is fast, so there is no need for an approximate index.
- **Retrieval test, 20 Nov 2026:** "Which states have the most late deliveries?" retrieved ex05 (similarity 0.9681), ex07 (0.9252) and ex06 (0.8845).

## D21. Embed only the question, and with the SEMANTIC_SIMILARITY task type
- **Chosen:** the index holds embeddings of the example *questions*. We embed the new question with the same task type (`SEMANTIC_SIMILARITY`) on both sides.
- **Alternative:** embed question plus SQL, or use the asymmetric `RETRIEVAL_QUERY` / `RETRIEVAL_DOCUMENT` types.
- **Why:** we are comparing a question with other questions. Adding SQL text to the vector would make the match depend on SQL words instead of what the user asks. Using the same task type on both sides keeps the comparison symmetric. The task type is part of the cache key, so changing it never returns stale vectors.

## D22. Only verified examples are indexed; RAG is on by default
- **Chosen:** `build_index.py` indexes only examples with `verified: true` (24 of 30 on 20 Nov 2026; ex24 and ex26-ex30 are not yet confirmed). RAG is the default and `--no-rag` gives the zero-shot prompt (`sql_v1`) for comparison. With RAG the prompt is `sql_v2`; a new prompt file means a new cache key.
- **Alternative:** index every drafted example without checking it.
- **Why:** a wrong example teaches a wrong pattern, and then the evaluation would measure our own mistakes. The `--no-rag` flag is how we compare configurations A (zero-shot) and B (RAG) in Phase 5.

**Update to D22 (20 Nov 2026):** Parth verified the last six examples (ex24, ex26-ex30), so all 30 are indexed. ex24 had its `delivered` filter removed (approval time is not a sales question, so rule 4 does not apply), and ex30 was re-tagged `traps: []` because it counts review rows and never averages per order. All 8 traps are still covered by other examples.

## D23. API design: plain FastAPI wrapper, 503 for model problems, no `httpx`
- **Chosen:** `api/main.py` has `POST /ask {question, use_rag}` and `GET /health`. The endpoint is a plain `def`, so FastAPI runs the blocking pipeline in a worker thread. `use_rag` defaults to true, and false gives the zero-shot mode. The request is validated (3-500 characters after trimming). If Gemini is unavailable (quota, overload), the API returns HTTP 503 with a short message, not a 500 crash. `/health` only checks that the database and index files exist; it never calls the LLM, so a health check cannot use up quota.
- **Alternative:** put the logic in the endpoint, or use FastAPI's `TestClient` for tests.
- **Why:** the API stays a thin wrapper over `pipeline.ask`, so the CLI, API and evaluation all run the same code. `TestClient` needs the `httpx` package, which is not in our approved dependency list, so the tests call the endpoint functions directly (with a mocked pipeline) and the real server is checked with `curl`.
- **Zero-call check (20 Nov 2026):** the server was started with a dummy API key, and a question already in the cache returned HTTP 200 with the full answer in 1.1 s. A real Gemini call with that key would have failed, so no API call was made.
